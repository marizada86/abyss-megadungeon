# Environment adapters — DRAFT r1

The shared ADD core owns canon precedence, conversation-bound checkpoints and preservation. A role defines domain inputs, knowledge references, outputs and checks; a native executor supplies tools and lifecycle when actually available. Neither a role file nor an adapter grants permissions.

Use the [catalog](catalog.json) as contracts to check, not claims of supported integrations. CLI runtime observations are operator reports; record exact project/environment/time and evidence of instructions loaded. Environment variables, client names and file installation do not prove capability or recognition. Do not serialize secret values, prior approvals, or another chat's cursor into portable observations.

For a bounded native task, supply role/revision, input paths/hashes/states, allowed reads/writes/actions, output, acceptance, cost/retry limits and integration owner. Give only relevant knowledge. Reconcile the actual result before the parent advances. Use sequential execution when native delegation or safe task isolation is unavailable. Self-review remains self-review.

A cloud/local handoff requires an explicitly scoped content manifest and privacy/rights review. Reauthenticate in the receiving environment. Keep canon and active approvals authoritative at their original project/conversation; a copied plan is context, not execution authority. Real shared-resource conflicts require coordination even when conversations have separate cursors.

Client validation levels: (1) files present, (2) installed payload verified, (3) instructions acknowledged with revision/hash, (4) bounded operation observed, (5) preserved state verified. Record only levels actually demonstrated; fixture success is not another machine/account or live Dot/cloud validation.
